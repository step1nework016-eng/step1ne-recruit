# 02｜AI Hard Gate 通用判斷引擎 v1.0

> 模組：Universal Pre-call Card  
> 用途：讓 AI 能針對任何職缺，判斷哪些條件屬於真正 Hard Gate、哪些只是 Nice-to-have，以及哪些需要電話中驗證。  
> 核心原則：**Hard Gate 不是 JD 關鍵字，而是「不符合時，是否會直接阻止推薦／任用」的條件。**

---

# 1｜設計目標

本規格的目的不是教 AI 判斷 BIM、職安、KA 或任何特定職缺。

而是建立一套可以跨職缺使用的通用判斷引擎。

AI 必須做到：

1. 從 JD / 客戶需求中找出所有可能條件
2. 區分：
   - Hard Gate
   - Nice-to-have
   - 待確認條件
3. 拿候選人資料與條件比對
4. 判斷：
   - 已符合
   - 待確認
   - 明確不符
5. UI 第一眼只顯示最重要、最需要顧問處理的 Gate
6. 不可因為某個職缺範例，而把特定產業邏輯套到所有職缺

---

# 2｜Hard Gate 核心定義

## Hard Gate

符合以下定義：

> **如果候選人不符合這個條件，會直接降低到「不能推、不能任用、或必須先解決才可繼續」的程度。**

常見類型：

- 必備能力
- 必備經驗
- 必備證照／資格
- 法規要求
- 工作地點接受度
- 輪班／外派／調派接受度
- 到職條件
- 特定語言或工具能力
- 其他直接阻止任用的條件

---

# 3｜Nice-to-have 定義

符合以下定義：

> **候選人沒有也可能被考慮，但有的話會提高優先順位或上手速度。**

常見用語：

- 尤佳
- 加分
- 優先
- 有經驗者佳
- 熟悉者佳
- 具備更佳

Nice-to-have 不可直接升級成 Hard Gate。

---

# 4｜待確認 Gate 定義

如果以下情況發生，AI 不得自行下結論：

- JD 用語模糊
- 客戶沒有明確說必要或加分
- 條件重要，但無法判斷是否「沒有就不能推」
- 候選人履歷證據不足
- JD 與客戶口頭需求互相矛盾

此時標記：

**待確認 Gate**

AI 不可擅自把它判成：

- Hard Gate
- Nice-to-have

---

# 5｜AI 判斷四層模型

AI 必須依照以下四層順序判斷。

---

## Layer 1｜來源強度

先判斷 JD / 客戶需求的措辭。

### 高強度詞

通常偏向 Hard Gate：

- 必須
- 需具備
- 至少
- 必要
- 不接受
- 需可配合
- 需持有
- 限定具備
- 最低要求

### 中強度詞

需要進一步判斷：

- 希望
- 熟悉
- 具備
- 相關經驗
- 可配合
- 有經驗

### 低強度詞

通常偏 Nice-to-have：

- 尤佳
- 加分
- 優先
- 更佳
- 有經驗者佳
- 熟悉者佳

---

# 6｜Layer 2：是否直接阻止任用

AI 自問：

> **如果候選人沒有這個條件，客戶還會不會考慮？**

如果答案是：

### 明確不會
→ Hard Gate

### 仍有可能
→ Nice-to-have

### 無法判斷
→ 待確認 Gate

---

# 7｜Layer 3：工作能不能做 vs 做得更好

AI 必須區分：

## 能不能做
偏向 Hard Gate

例如：

- 必須會某核心工具
- 必須有法定證照
- 必須可輪班
- 必須可外派
- 必須可在特定地點工作

## 做得更好
偏向 Nice-to-have

例如：

- 有大型專案經驗
- 有相同品牌經驗
- 有完全相同產業經驗
- 熟悉更多工具
- 有管理經驗但非必要

---

# 8｜Layer 4：證據是否足夠

即使 JD 明確寫 Hard Gate，AI 也不能只因候選人履歷出現關鍵字就判定「符合」。

AI 必須看：

- 是否真的做過
- 做多久
- 做到哪一層
- 是否獨立負責
- 是否只是協助
- 是否有實際成果
- 是否有規模證據
- 是否只是課程／學校／證照接觸

---

# 9｜候選人 Gate 狀態

每個 Gate 只能使用以下 3 種狀態：

## ✅ 已符合

需要有明確證據。

例如：

- 履歷明確寫「獨立使用 Revit 建模 2 年」
- 明確列出「負責屈臣氏與寶雅通路」
- 明確寫「持有乙級職安證照」

---

## ❓ 待確認

適用：

- 履歷有關鍵字，但深度不明
- 工作內容寫得太廣
- 地點接受度未知
- 輪班／外派意願未知
- 年資或責任範圍不清楚

---

## ⛔ 明確不符

需要有明確衝突。

例如：

- 職缺要求台中長期派駐，候選人明確表示只接受台北
- 必須持有證照，但候選人明確沒有且短期無法取得
- 職缺要求 3 年以上經驗，而候選人只有 3 個月，且客戶不接受例外

---

# 10｜Hard Gate 分類

AI 應將 Gate 分成以下類型。

## A｜能力 Gate

例如：

- Revit 實作
- 程式開發能力
- 職安管理
- KA 通路操作
- 財務分析

---

## B｜經驗 Gate

例如：

- 3 年以上現場經驗
- 開架通路經驗
- B2B 業務經驗
- 特定產業背景

---

## C｜資格 Gate

例如：

- 證照
- 駕照
- 工作資格
- 專業執照

---

## D｜現實條件 Gate

例如：

- 工作地點
- 輪班
- 外派
- 出差
- 到職時間
- 薪資底線
- 工作型態

---

# 11｜UI 顯示規則

AI 在後台可以保存全部 Gate。

但 Pre-call Card 第一眼：

**最多顯示 3 個**

顯示優先序：

1. 待確認且會直接影響推薦
2. 明確不符但仍值得電話確認
3. 高風險現實條件
4. 已符合的重要 Gate

---

## 已符合 Gate

預設折疊。

原因：

顧問電話前最需要看的是：

> **還沒確認什麼**

不是：

> **已經知道什麼**

---

# 12｜Gate 排序公式

AI 可使用以下概念排序：

```text
Gate Priority =
任用阻斷程度
×
目前不確定程度
×
電話可驗證程度
```

優先顯示：

- 會阻止推薦
- 現在不知道
- 電話中可以問清楚

---

# 13｜AI 不可做的事

禁止：

- 只看 JD 關鍵字就判 Hard Gate
- 把「尤佳」當必要
- 把「熟悉」自動當 Hard Gate
- 因為某職缺常見要求，就自行補條件
- 因為過去 BIM 案例，就對其他工程職亂套
- 因為候選人有某關鍵字，就直接判符合
- 把所有條件都列成 Hard Gate
- 自行創造客戶沒有提過的淘汰條件

---

# 14｜不確定處理規則

如果 AI 無法確定條件是否真正阻斷任用：

必須：

1. 標記為 `pending_gate`
2. 說明原因
3. 不可直接淘汰
4. 可建議顧問／客戶確認

範例：

```yaml
gate:
  criterion: "乙級職安證照"
  classification: "pending_gate"
  reason: "JD 有列出證照，但同時提到到職後可補助考取，無法判斷是否為到職前必要條件"
```

---

# 15｜AI 結構化輸出

```yaml
hard_gate_analysis:

  gates:
    - criterion: ""
      category: "ability | experience | qualification | work_condition"
      source_strength: "high | medium | low"
      classification: "hard_gate | nice_to_have | pending_gate"
      candidate_status: "matched | unknown | unmatched"

      evidence:
        jd_evidence: ""
        candidate_evidence: ""

      reason: ""
      verify_in_call: true
      priority: "high | medium | low"
```

# 16｜標準壓力測試案例

---

## Case A｜BIM 工程師

### 條件

- Revit / AutoCAD
- 願意進半導體廠
- 苗栗銅鑼
- MEP 經驗佳

### 判斷

| 條件 | 分類 |
|---|---|
| 基本 Revit / AutoCAD | Hard Gate 或待確認 Gate，依客戶最低要求 |
| 銅鑼地點接受度 | Hard Gate |
| 無塵室／半導體廠工作型態 | Hard Gate |
| MEP 經驗 | Nice-to-have，除非客戶明確要求 |

---

## Case B｜職安工程師

### 條件

- 3 年以上現場實務
- 承攬商管理
- 可調派
- 乙級技術士尤佳

### 判斷

| 條件 | 分類 |
|---|---|
| 現場實務 | Hard Gate |
| 承攬商／巡查實務 | Hard Gate |
| 可調派 | Hard Gate |
| 乙級技術士 | Nice-to-have，若公司接受到職後補考 |

---

## Case C｜Key Account 業務

### 條件

- 3 年開架通路
- 熟悉屈臣氏／康是美／寶雅
- 談判經驗
- 管理領導經驗

### 判斷

| 條件 | 分類 |
|---|---|
| 開架通路實務 | Hard Gate 或待確認 Gate，依客戶要求 |
| 採購／商務談判 | 核心能力 Gate |
| 年度業績責任 | 核心能力 Gate |
| 管理領導 | 若非帶人職，通常 Nice-to-have |

---

## Case D｜行政專員

### 條件

- Office 文書
- 細心
- 行政經驗
- 英文佳

### 判斷

| 條件 | 分類 |
|---|---|
| 基本文書能力 | Hard Gate |
| 行政流程經驗 | 視職缺複雜度判斷 |
| 細心 | 不可單靠主觀描述當 Gate |
| 英文佳 | Nice-to-have，除非實際工作每天需要英文 |

---

## Case E｜軟體工程師

### 條件

- Python
- 3 年以上 Backend
- AWS
- Docker
- FinTech 經驗佳

### 判斷

| 條件 | 分類 |
|---|---|
| Python | 若核心開發語言，Hard Gate |
| Backend 經驗 | Hard Gate |
| AWS | 視實際工作依賴程度 |
| Docker | 視實際工作依賴程度 |
| FinTech 經驗 | Nice-to-have，若寫「佳」 |

---

# 17｜AI 自我檢查

生成完成後必須問：

### Check 1
這個 Gate 若不符合，真的會讓候選人不能推嗎？

### Check 2
這是客戶要求，還是 AI 自己推測？

### Check 3
JD 用語是必要，還是只是加分？

### Check 4
候選人真的有證據符合，還是只是出現關鍵字？

### Check 5
這個條件是否應該放在電話中確認？

### Check 6
主畫面是否超過 3 個 Gate？

---

# 18｜強制失敗條件

只要出現任一情況，視為生成失敗：

- 所有 JD 條件都被判成 Hard Gate
- 「尤佳／加分／優先」直接被判成 Hard Gate
- AI 自行新增客戶未提出的淘汰條件
- 候選人只出現技能關鍵字就被判符合
- Gate 超過 3 個仍全部顯示在主畫面
- 無法說明為何此條件會阻止任用
- Gate 判斷只適用某個特定產業
- 無法套用到行政、業務、工程、技術等不同職類

---

# 19｜與「這通電話只要確認」的串接

Hard Gate Engine 產出後：

1. 找出 Priority 最高的 2～3 個待驗證 Gate
2. 傳給 `call_goal.validation_points`
3. 每個 Gate 再生成一個「必問問題」
4. 已符合 Gate 收折
5. 明確不符 Gate 需顯示警示

流程：

```text
JD
↓
條件解析
↓
Hard / Nice / Pending 分類
↓
候選人證據比對
↓
Matched / Unknown / Unmatched
↓
取 Top 2–3 Gate
↓
這通電話只要確認
↓
今天必問 3 題
```

---

# 20｜核心原則

> **通用的是判斷方法，不是職缺內容。**

AI 不應學會：

> BIM 要問 Revit

而應學會：

> 哪一個條件不符合，會真的阻止推薦？
