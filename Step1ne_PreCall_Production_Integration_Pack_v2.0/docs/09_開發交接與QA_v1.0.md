# 09｜開發交接與 QA 規格 v1.0

> 模組：Step1ne Pre-call Production Integration  
> 用途：提供 Claude Code / Codex / Backend / Frontend 作為 Phase 1 實作、驗收、回歸測試與交付報告的最終交接文件。  
> 依據：`PRECALL_INTEGRATION_AUDIT.md`、規格 00～08。  
> 目前範圍：**Phase 1 — Read-only Pre-call Card**  
> 核心原則：**先證明 Pre-call Card 對顧問真的有用，再進 Call Mode、Gate Result 與 Post-call Decision。**

---

# 1｜Phase 1 目標

Phase 1 的唯一產品目標：

> **把現有「電洽前準備」從自由文字升級成一張 60～90 秒可讀完、結構化、ADHD 友善的 Pre-call Card。**

Phase 1 成功標準不是：

- 新增多少 AI 功能
- 做多少新 DB
- 做多少新頁面

而是：

> 顧問能不能更快知道「這通電話要確認什麼、要問哪三題、最大的風險在哪」。

---

- [ ] 顯示 Candidate Summary

- [ ] 最多顯示 3 個 Hard Gate
- [ ] 最多顯示 3 個 Must Ask

- 新 Pipeline enum

# 4｜Production Source of Truth 驗收

必須確認：

## Job

來源：

`jobs`

不得複製成：

- precall_jobs
- job_snapshot table
- second JD table

---

## Candidate × Job

來源：

`applications`

不得建立第二個：

- candidate_job_match
- precall_candidate
- precall_application

除非未來經過獨立 Architecture Review。

---

# 5｜Hard Gate Source 驗收

正式優先序：

```text
1. jobs.hard_filters
2. jobs.must_check_items
3. jobs.required_conditions
4. jobs.client_screen_conditions
5. AI fallback
```

---

## 驗收條件

如果：

`jobs.hard_filters`

已有資料：

AI 必須優先使用既有 Gate。

AI 可以：

- 重新排序
- 精簡顯示名稱
- 對照候選人證據
- 判 matched / unknown / unmatched
- 決定 verify_in_call

AI 不可以：

- 完全忽略 Production Gate
- 重新生成另一套互相衝突的 Gate
- 因自身一般知識加入客戶沒要求的淘汰條件

---

# 6｜Hard Gate Candidate Compare

必須區分：

## Job Gate

回答：

> 這個職缺需要什麼？

## Candidate Gate Status

回答：

> 這個候選人目前對這個 Gate 的證據是什麼？

兩者不可混合。

---

# 7｜Status Mapping 驗收

Production 現有：

```text
pass
partial
unknown
```

Pre-call Contract：

```text
matched
unknown
unmatched
```

正式 mapping：

```text
pass    → matched
partial → unknown
unknown → unknown
```

---

## unmatched 規則

只能有明確負面證據時產生。

例如：

- 候選人明確拒絕必要地點
- 必要資格確定沒有
- Hard Fail 已被 Production 證實
- 客戶必要條件明確不符

禁止：

```text
partial → unmatched
```

---

# 8｜Call Goal QA

必須符合：

- [ ] 指向目前 Job
- [ ] Decision 清楚
- [ ] 2～3 個 Validation Points
- [ ] Validation Point 能連到 Gate
- [ ] 不超過 UI 容量
- [ ] 不寫「了解背景／確認適配度」等空話

範例：

```text
確認是否能推「BIM 工程師」

Revit 實作
機電整合
銅鑼／無塵室
```

---

# 9｜Must Ask QA

每題必須：

- [ ] 有 `id`
- [ ] 有 `question`
- [ ] 有 `validates_gate_id`
- [ ] `validates_gate_id` 找得到 Gate
- [ ] 有 `why_it_matters`
- [ ] 不超過 3 題
- [ ] 不是把 JD 改成問句
- [ ] 不重問履歷已知內容
- [ ] 優先問實務證據

---

# 10｜正式欄位名稱

唯一正式名稱：

```text
validates_gate_id
why_it_matters
```

Legacy Compatibility Layer 可接受：

```text
validates
validates_gate
why
```

但 API Response 不得再輸出 legacy field。

---

# 11｜AI Flag QA

Primary Flag：

最多：

**1 個**

必須：

- [ ] 有證據
- [ ] 會影響推薦或電話策略
- [ ] 有具體 Action
- [ ] 不是 Nice-to-have 缺失
- [ ] 不是人格推測
- [ ] Unknown 沒被誤寫成不符合

如果沒有值得提醒：

```json
"ai_flags": []
```

這是正常結果。

---

# 12｜Candidate Summary QA

`name`

必須來自 Production。

AI 不得改名。

---

`current_role`

可 runtime derived。

若不確定：

`null`

---

`relevant_experience`

可 derived。

不可回寫成 Candidate Source of Truth。

---

`location_summary`

不可把：

`applications.location_ok`

誤當成地點文字。

---

# 13｜Job Context QA

所有 Job Facts：

- title
- locations
- salary
- work mode
- hours
- employment

必須來自 `jobs`。

AI 不得自行改寫金額、地點或工作條件。

---

# 14｜Schema Validation QA

至少驗證：

- Root required fields
- schema_version
- application_id
- job_slug
- hard_gate enum
- status enum
- question count
- flag count
- Gate ID relationships
- array types
- null handling

---

# 15｜Malformed AI Output

如果 AI 回傳：

- 缺欄位
- 多餘舊欄位
- JSON parse error
- Gate reference 失效

Backend 必須：

1. normalization（只有安全時）
2. validation
3. retry 或 fallback

Frontend 不得自己修 JSON。

---

# 16｜API QA

---

## GET

```text
GET /admin/application/:id/precall-card
```

測試：

### Ready

期待：

```text
status = ready
```

### Not Generated

期待：

```text
status = not_generated
```

### Stale

期待：

```text
status = stale
```

### Missing Application

期待：

```text
APPLICATION_NOT_FOUND
```

---

## POST

```text
POST /admin/application/:id/precall-card
```

Body：

```json
{
  "force": false
}
```

測試：

- valid cache
- no cache
- force regenerate
- processing duplicate request
- AI failure
- resume missing

---

# 17｜Concurrency QA

同一 application 正在產生 Pre-call：

再次 POST：

不得再新增第二個相同 AI job。

必須：

- 回 existing job
- 或明確 processing response

---

# 18｜Idempotency QA

相同：

- application
- job
- resume
- fingerprint

且：

`force=false`

期待：

不重複呼叫 AI。

---

# 19｜Cache QA

若實作 cache：

必須確認：

- Job 更新 → stale
- Resume 更新 → stale
- Schema version 更新 → stale
- force regenerate → 新生成
- cache parse error → invalid + retry/fallback

---

# 20｜Fallback QA

如果新 Pre-call 生成失敗：

且：

`call_prep_md`

存在。

UI 顯示：

Legacy Pre-call。

不能：

整個 Candidate Drawer crash。

# 27｜Empty Data QA

- Job 有資料

# 28｜No Hard Filters QA

如果：

`jobs.hard_filters = empty`

```text

```

---

# 29｜Complete Hard Filters QA

如果已有完整：

`hard_filters`

期待：

```text
used_ai_fallback_for_gates = false
```

AI 不重新創造另一套。

---

# 30｜Nice-to-have QA

Job：

```text

```

候選人：

沒有。

期待：

不能因此：

- unmatched
- High AI Flag
- pause recommendation

# 31｜Sensitive Attribute QA

任何：

- 年齡
- 性別

- 政治

不可作為：

- Gate
- Flag
- Match Status

# 36｜顧問體驗驗收

至少找實際顧問測：

## 任務

給一個 Job＋Candidate。

要求：

> 請在打電話前快速看這張卡。

測量：

1. 是否 60～90 秒內看完
2. 是否知道這通電話目標
3. 是否知道最重要三題
4. 是否知道哪裡有風險
5. 是否還會回去重讀完整履歷

---

# 37｜顧問測試問題

測試完問：

- 你第一眼先看哪裡？
- 哪個區塊最有用？
- 哪個區塊可以刪？
- 三題有沒有真的想問？
- Gate 看得懂嗎？
- Flag 有沒有多餘？
- 你會不會真的每天用？

---

# 38｜Phase 1 Product Acceptance

符合以下才算成功：

- 80% 以上測試個案能在 90 秒內完成 Pre-call Scan
- 顧問能正確說出主要 Call Goal
- 顧問能直接使用至少 2/3 AI Questions
- 不需要重新閱讀完整 JD 才知道工作條件
- 沒有重大 Hard Gate 誤判
- 沒有把 Unknown 誤淘汰
- 沒有破壞 legacy flow

注意：

以上為產品驗收目標，不是自動化測試硬性 KPI。

# 41｜Pending Product Decision 03：電話前路徑提示

原 UI Reference 有：

```text
符合
部分符合
不符合
```

建議 Phase 1 弱化或移除。

原因：

真正五態 Decision 屬於電話後。

電話前最多顯示：

```text
通過 → 可推薦
資訊不足 → 補資料
Gate 不符 → 再判斷其他方向
```

不要在電話前強做 Post-call Decision。

---

# 42｜Pending Product Decision 04：Partial UI Copy

Production：

`partial`

Adapter：

→ `unknown`

UI 建議文字：

```text
待確認
```

搭配 evidence：

```text
已有部分證據，但仍不足以確認
```

不要顯示：

```text
部分符合
```

避免顧問誤以為已經接近通過。

# 51｜核心原則

> **Production Source of Truth 不重建。**

> **AI Unknown 不等於不符合。**

> **顧問的注意力比 AI 輸出量重要。**

> **Phase 1 先把「看懂」做好，再把「寫入與自動化」加上去。**
