# E21（階段二）：電話錄音轉逐字稿——模型已裝、實測完成（wsl2，2026-10-12）

> 階段一（程式與 Worker patch）見 `E21_錄音轉逐字稿_階段一_*.md`。這份是裝模型、實測、修正之後的結果。Jacky 10/12 在對話裡明確說「可以下載」才下載。

## 結論
- 可用：本機 faster-whisper large-v3（int8、CPU），錄音不離開這台、沒有雲端轉錄。端到端模擬（真的轉文字＋假 TG＋假確認卡）通過，暫存檔都刪乾淨。
- **加專有名詞提示明顯有用**：1 分鐘的測試音檔，錯字率 2.4% → 1.2%，4 個專有名詞全對（鼎新 T100、商周集團、宣捷生技、BOM 表）。
- **實測發現並修了三個問題**（見第 3 節）：簡體字、長檔重複迴圈（也讓速度慢 3 倍）、尾巴吐出提示詞清單。
- **限制**：測試音檔是 Windows 合成語音（zh-TW Hanhan），比真人電話乾淨很多。真實準確度要等 Jacky 傳第一個真實錄音才知道；沒有說話者分段。
- 這台的 ai_worker 現在會在「沒有面談」時認領 call_audio 工作（venv 已裝好）。Worker patch 還沒部署，所以目前不會有工作進來。

## 1. 安裝（都經 Jacky 在對話同意）
- `~/.venvs/call_audio`：faster-whisper 1.2.1（PyPI），約 461 MB。**相依套件 `av` 要釘在 15.1.0**：預設裝到的 19.0.1 與 faster-whisper 1.2.1 不相容（`open() got an unexpected keyword argument 'metadata_errors'`）。
- 模型 Systran/faster-whisper-large-v3（Hugging Face，約 2.9 GB，`~/.cache/huggingface`），在確認沒有面談時下載。之後執行都是 `local_files_only`。

## 2. 準確度（短檔，1 分鐘，7 句，含「商周集團、鼎新 T100、宣捷生技、BOM 表」）
| 設定 | 字元錯誤率 | 專有名詞 | 備註 |
|---|---|---|---|
| 完全不給提示 | 4.8% | 3/4 | 「宣捷」→「宣潔」；輸出夾雜簡體字（履历、几、后、万），`zh_trad` 為了不轉錯是保守的，沒轉 |
| 只給繁體基礎提示（沒有專有名詞時的行為） | 2.4% | 3/4 | 簡體字消失；「鼎新」→「頂新」 |
| 完整提示（initial_prompt＋hotwords） | **1.2%** | **4/4** | 剩下的差異只有標點與「十二萬」→「12萬」 |
- 錯字率是去掉標點與空白後，與原稿的字元編輯距離。7 句、約 175 字，樣本很小，只能說「方向明確」，不能說「準確度 98.8%」。
- 「鼎新」一開始被聽成「鼎興」，原因是 `extract_terms` 只抓到 T100 沒抓到前面的廠牌。已修：「中文詞＋英數代號」會把中文詞也列入（一般詞如「系統」「版本」排除）。

## 3. 實測發現並已修正
1. **簡體字**：不給提示時 Whisper 會輸出簡體。修：沒有專有名詞也一律帶「以下是繁體中文的獵頭顧問與人選電話訪談。」（`BASE_PROMPT`）。
2. **長檔重複迴圈＋慢**：預設 `condition_on_previous_text=True` 時，5 分鐘切片出現 5 處連續重複行、耗時 489 秒（1.63× 即時）。關掉後 0 處連續重複、169 秒（0.56× 即時），快約 3 倍。代價：`initial_prompt` 只作用在第一個視窗，所以專有名詞另外用 hotwords 帶（每個視窗都有效）；後段標點偶爾變成空格（內容不受影響）。另外加兩道保險：連續重複句收斂（`collapse_repeats`）、`compression_ratio_threshold=2.0`。
3. **提示詞回聲**：切片結尾 Whisper 把 hotwords 清單原樣當文字吐出（「宣捷生技 鼎新 T100 BOM 財務經理 成本會計」）。修：整行只剩 ≥2 個專有名詞就丟掉（`strip_term_echo`）。
- 測試：`tests/call_audio_test.py` 新增 5 項（回聲、重複收斂、基礎提示、鼎新抽取等），全過。

## 4. 耗時與 CPU（16 核機器，8 執行緒，`nice 10`）
- 1 分鐘檔：34–38 秒（含載入模型約 10 秒），CPU 約 224–253 CPU 秒。
- **15.1 分鐘檔，舊設定（條件開）**：牆鐘 **1595 秒（26.6 分，1.76× 即時）**，約 7.5 核。
- 5 分鐘切片，新設定：beam 5 → 169 秒（0.56×）；beam 1 → 143 秒（0.48×，輸出與 beam 5 幾乎相同）。**推算 15 分鐘檔約 8.5 分鐘**（推算，沒有整檔重跑）。預設維持 beam 5，真實電話音質較差時束搜尋可能有幫助；若要更快可設 `CALL_AUDIO_BEAM=1`。
- CPU 約佔 7 核，`nice 10`，且只在沒有阿財面談時開始。**沒有測「轉文字進行到一半有面談進來」對阿財回覆秒數的影響**——這是還沒驗證的風險。想更保險可把 `CALL_AUDIO_THREADS` 降到 4（速度約減半）。

## 5. 長檔測試的限制（請勿引用長檔的錯字率）
長檔 `long.wav` 是用重複的腳本合成的（原稿 153 句中有 136 句是重複），所以第一次算出的 28.9% 錯字率**不成立**，我不採用。長檔只用來量耗時與觀察重複迴圈。
