# 回報（WSL2）：社群串文「最後一則」延遲 41 分鐘／缺漏／重複 — 發文沒有逐則驗證

日期：2026-10-21　　起因：Jacky 回報「DR 串文第 4 則沒有發出去」（排隊編號 #992，帳號 4 DR，職缺 pending-so-264270ce）

## 結論（有證據）
**根因在 Worker 的串文發文流程（`src/index.js` `soc_approve` → `postOne` 迴圈，約 5109～5237 行）：每一則只拿到 Threads 回傳的 id 就當成功，沒有確認那則真的出現在串文裡，也沒有重試或補發。** Threads 偶爾在某一則卡住幾分鐘，卡住的那則會晚很久才出現、甚至不出現，資料庫卻早已寫成「已發」。

## 為什麼會這樣（程式碼）
- `postOne()`：建立 container → `sleep(5000)` → `threads_publish`，只檢查 HTTP 成功與回傳有 `id`，**沒有再去讀 Threads 確認這一則真的公開了**。
- 迴圈 `for (const chunk of chunks) lastId = await postOne(chunk, lastId)` 任何一則卡住，整個請求就卡在那；結束後直接 `status='posted'`。
- 失敗時（`catch`）只把狀態重設成可重按並發 TG 通知；**成功但晚出現／沒出現的情況沒人知道**。#969 多出的兩則（13～15 小時後）很像有人看到缺一則重按或重送，造成重複。

## 建議修法（請 Mac 在 Worker 改，WSL2 沒有部署權限）
1. 每則 `threads_publish` 後讀 `GET /{published_id}?fields=id,timestamp,permalink`，確認存在再發下一則；讀不到就等待重試（例如 3 次、每次 10 秒），仍失敗就**中止並把「已發到第幾則、缺哪幾則」寫進佇列**（新增欄位或寫在 `social_post_queue`），不要標 `posted`。
2. 標成 `posted` 之前，用 `conversation` 數一次實際則數，少於 `chunks.length` 就標成 `partial` 並發 TG（帶缺的第幾則）。
3. 補發按鈕：只補缺的那幾則，接在「最後一則已存在的回覆」底下，不要重發整串（避免像 #969 的重複）。
4. 加上計時 log：每一則 create／publish 各花幾秒，超過 60 秒就發 TG。
