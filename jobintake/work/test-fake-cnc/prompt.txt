# 職缺上架工作流程

這個流程是從 step1ne.com 的實際上架經驗萃取出來的。每一條「禁刊」規則都對應
一次真實踩到的狀況——不是通用範本抄來的checklist。

## Phase 0 — 設定（每台電腦/每個站只需確認一次）

先確認以下三項，缺任何一項就先問使用者，不要猜：

| 項目 | 說明 |
|---|---|
| 網站原始碼路徑 | 本機 clone 的位置，例如 `~/專案/<site>/` |
| Git remote | 部署用的 repo；若接了自動部署，push 即上線 |
| 職缺路徑慣例 | 建議 `/jobs/<slug>/index.html`，專區在 `/jobs/index.html` |

若在別的機器或別的站執行，改成該環境的實際值。**不要假設路徑存在，先 `ls` 確認。**

## Phase 1 — 讀來源，抽出欄位

把 JD 檔案讀進來（PDF 用 Read 的 pages 參數；Excel 用 openpyxl；圖片型 PDF 用視覺讀取）。
抽出這些欄位，缺的就標「未提供」，**不要自己編**：

職稱／工作地點／職務性質／需求人數／薪資／學歷／年資／必要條件／加分條件／
語言／證照／加班／休假／上班時間／福利／出差／轉正條件

### ⚠️ 來源是 Google 試算表時：一定要先檢查隱藏狀態

**這是實測踩過的坑。** 用一般方式讀 Google Sheets（`read_file_content` 或
複製貼上文字），會把**隱藏的分頁與隱藏的列一併讀進來**，而且完全看不出哪些
是隱藏的。實際案例：一份表用文字讀有三十幾個職缺，實際只有 12 個該上架，
其餘全在隱藏分頁裡（已關閉或不需要的職缺）。照單全收就會把已經填滿的職缺
刊上網站。

**正確作法**：下載成 XLSX，用 openpyxl 讀結構：

```python
import openpyxl
wb = openpyxl.load_workbook("下載的檔案.xlsx")
for ws in wb.worksheets:
    hidden_rows = [r for r, d in ws.row_dimensions.items() if d.hidden]
    print(ws.sheet_state, ws.title, "隱藏列:", hidden_rows)
    # ws.sheet_state == 'hidden' → 整個分頁不要用
```

從 Google Drive 取得 XLSX：`download_file_content` 並指定
`exportMimeType = application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`
（回傳 base64，解碼後存檔）。

**只處理**：`sheet_state == 'visible'` 的分頁 × 沒有 `hidden` 的列。

**順便讀底色**：客戶常用底色標記狀態（實際案例：淡紅 `FFF4CCCC` = 急件）。
`ws.cell(row=r, column=1).fill.start_color.rgb` 可以讀到。**但底色代表什麼
意思一定要問使用者**，不要自己假設——同一份表裡紅底有的被隱藏、有的沒有，
代表底色與隱藏是兩套獨立標記。

## Phase 2 — 禁刊過濾器（最重要，先跑這關）

讀 `references/publishing-filters.md`，逐條比對。命中任一條就從公開內容移除，
並記錄下來，Phase 7 要跟使用者回報「擋掉了什麼」。

摘要（完整說明與改寫範例在 reference）：

| 禁刊類型 | 為什麼 |
|---|---|
| 委任客戶公司名稱 | 客戶保密義務；改用「國際半導體大廠」「製造業集團」等產業描述 |
| 歧視性條件（國籍/年齡/性別/婚育/容貌） | **違反就業服務法第5條，會被裁罰**；年齡類改寫成「歡迎職涯初期人才」 |
| 內部獵頭搜尋策略（建議鎖定產業、建議搜尋職稱清單） | 等於把挖角名單公開給同業 |
| 內部溝通備註 | 例：「客戶最初說 25-30 人，與確認的 20 人有落差，建議二次確認」 |
| 標註「待確認」的欄位 | 不刊未驗證資訊；列進待確認清單請使用者補 |

## Phase 3 — 判服務線

不同服務線的頁面呈現不一樣，判錯會讓高階人選覺得被當成派遣工：

| 訊號 | 判定 | 頁面要怎麼寫 |
|---|---|---|
| 年薪百萬以上、主管職、需保密 | **高階獵才** | 標籤「高階獵才」；應徵流程寫「顧問保密初談」；必加「我還在職，投遞會不會曝光？」FAQ |
| 派遣雇主是自家公司、有轉正條件、時薪/月薪制基層職 | **人力派遣** | 標籤「人力派遣」；必加「派遣權益跟正職一樣嗎？」FAQ（用勞基法角度，不要寫成內部作業說明） |
| 一般企業委託代招正職 | **正職招募** | 標籤「正職」；標準版 |

判不出來就問使用者，不要預設。

## Phase 4 — 改寫 JD

**絕不把客戶原文直接貼上網站。** 三個原則：

1. **求職者視角**：客戶寫「BIM 相關技術工作（產能設計、建模、管理協調類）」→
   改成「使用 Revit 等 BIM 軟體建立與維護建築資訊模型，支援專案各階段需求」
2. **拿掉內部作業口吻**：「由 Step1ne 投保勞健保、發放薪資」→
   「權益依勞基法辦理，與一般受僱者相同」（放 FAQ，不放規格表）
3. **硬條件進規格表**：薪資/地點/年資/學歷這些要一眼看完，不要埋在 FAQ 折疊區裡

薪資揭露判斷：
- 有具體數字 → 公開區間（AEO 與 JobPosting schema 都吃這個，是強項不是風險）
- 客戶給的是**學歷分級表**（例：普通大學 35K／前四大 43K）→ **只公開總區間**，
  不公開分級細節，避免被解讀成學歷歧視
- 純面議 → 頁面寫「依經驗面議」，schema 不放 `baseSalary`

## Phase 4.5 — 同名職缺區隔規則（站上已有相同／相似職稱時必跑）

上架前先查站上有沒有同職稱的缺。不同客戶開出職稱一模一樣的職缺是常態，
不處理會同時壞掉三件事：求職者選錯、Google 兩頁互搶、阿財抓錯 JD。

**先查再寫**（D1 資料庫 `step1ne-recruit`）：

```bash
npx --yes wrangler d1 execute step1ne-recruit --remote \
  --command="SELECT slug,title,locations,employment,salary_min,salary_max FROM jobs WHERE title LIKE '%客服%';"
```

### 規則 1：對外標題只能用求職者分得出來的差異

可以用的區隔維度（照這個順序挑，先挑求職者最在意的）：

| 維度 | 標題寫法範例 |
|---|---|
| 班別 | 遊戲客服（早班）／遊戲客服（晚班／夜班加給） |
| 薪資帶 | 遊戲客服（月薪 31K）／遊戲客服（月薪 38–42K） |
| 僱傭型態 | 遊戲客服（派遣轉正）／遊戲客服（直聘正職） |
| 外語加給 | 遊戲客服（中文）／遊戲客服（日文加給 5K） |
| 地點 | 遊戲客服・台北內湖／遊戲電話客服・新北中和 |

**絕對禁止**：用「A 公司／B 公司」「甲客戶／乙客戶」「某遊戲大廠 A」這類指向客戶的字眼區隔。
連編號都不行——同業一比對就知道你有幾個客戶、分別在招什麼。
這條等同 Phase 2 的「委任客戶公司名稱」禁刊，區隔需求不構成例外。

### 規則 2：內部用 `client_code` 區分，不對外顯示

`jobs.client_code` 是顧問內部的客戶代號。**任何對外輸出都不得出現**：
不進頁面 HTML、不進 schema、不進網址、不進職缺卡、不進申請表選單文字、
不進給候選人的信與 AI 面談逐字稿。它只出現在顧問後台與內部報表。

驗證方式（Phase 6 會再跑一次）：`client_code` 的值不得出現在任何 `jobs/*/index.html`。

### 規則 3：slug 必須唯一且能自我說明

slug 要讓人不開頁面就知道是哪一個。格式：`<領域>-<職務>-<地點>-<區隔>`

- ✅ `game-cs-neihu-day` / `game-cs-neihu-shift`
- ✅ `mobile-game-cs-neihu` / `game-phone-cs-zhonghe`（現行做法，靠地點區分）
- ❌ `game-cs-2`、`game-cs-b`、`game-cs-new`（看不出差別，日後沒人知道哪個是哪個）
- ❌ slug 裡放客戶代號或客戶名

### 規則 4：兩頁高度相似要處理 SEO 互搶

這是 `seo-bottleneck-diagnosis` 八環模型第 4 環（關鍵字互搶）：兩頁講同一件事，
Google 不知道要排哪一個，結果兩頁都排不上去。二選一：

- **兩頁都要留**（兩個客戶都在招）→ 標題、導言、工作內容必須有**實質差異**，
  不能只改一個詞。把區隔維度寫進 H1、`<title>`、meta description 與導言第一句。
- **其實是同一個缺的變體**（同客戶不同班別）→ 合併成一頁、班別做成規格表的一列，
  或保留兩頁但把次要那頁 `<link rel="canonical">` 指向主頁。

不確定要不要合併時，判準是：**求職者會不會兩個都投？** 會 → 分兩頁；不會 → 合併。

### 規則 5：申請表下拉選單一定要顯示區隔字串

阿財（AI 面談）靠 `applications.job_slug` 去 `jobs` 抓 JD 與面談條件。選錯的後果不是小事：
**用錯條件面談，報告也歸錯客戶**。所以申請表的職缺選單不能只顯示職稱，
必須顯示「職稱＋區隔字串」，跟頁面標題完全一致，例如：

- `遊戲客服（早班／中班）・台北內湖`
- `遊戲電話客服（早班／晚班）・新北中和`

### 現況佐證（真實資料，可直接當範例）

站上這幾筆同為「遊戲客服」，職稱、月薪 31K、僱傭型態（派遣＋全職）全部一樣，
**只剩地點與班別能區分**：

| slug | 對外標題 | 地點 |
|---|---|---|
| `mobile-game-cs-neihu` | 遊戲客服（早班／中班） | 台北市內湖區 |
| `game-phone-cs-zhonghe` | 遊戲電話客服（早班／晚班） | 新北市中和區 |
| `payment-cs-night-zhonghe` | 金流客服 | 新北市中和區 |
| `fnb-brand-cs-zhonghe` | 餐飲品牌客服 | 新北市中和區 |

同區三筆客服全在中和、薪資帶相同，靠的是**服務領域**（遊戲／金流／餐飲）區分——
這已經是可用區隔的極限。再多開一個中和的遊戲客服，就一定要動班別或薪資帶，
否則兩頁必然互搶。

### 相關欄位：`ai_disclosure` 與 `client_named`

同一批新增的兩個欄位，上架時要一併確認（顧問決定，不要自己填）：

| 欄位 | 值 | 對頁面的影響 |
|---|---|---|
| `client_named` | 1 = 已簽約可具名 | 頁面可寫客戶名 |
| | 0 = 未簽約必須匿名 | 走 Phase 2 匿名化，一律用產業描述 |
| `ai_disclosure` | `always` | 頁面／應徵流程要寫明初步面談由 AI 進行 |
| | `by_client` | 依客戶個案決定，先問顧問 |
| | `never` | 不揭露 AI，面談流程改用中性描述 |

沒有值就是還沒決定，**先問使用者**，不要預設 `always`／`1`。

## Phase 5 — 產生頁面

讀 `references/page-template.md` 取得版型結構與必備元素。

頁面區塊順序（實測後定案，硬條件要在最前面）：
Hero（麵包屑＋標籤＋H1＋一段導言）→ **職缺條件一覽（規格表）** → 工作內容 →
應徵條件（必要/加分）→ 為什麼選這個機會 → 應徵流程 → FAQ → CTA

同時更新：
- `/jobs/index.html` 加一張職缺卡（含 `data-cat` 產業分類、服務線標籤）
- 需要新產業分類就加一顆篩選按鈕
- `sitemap.xml` 加該頁網址

## Phase 7 — 回報後再部署

**預設不自動 push。** 先給使用者這三份清單：

1. **已刊登**：職缺名稱、網址、薪資與服務線判定
2. **擋掉了什麼**：每條禁刊命中 + 原因（讓使用者知道你沒有偷偷吃掉資訊）
3. **待你確認**：來源標「待確認」或未提供、但求職者會問的欄位

使用者確認後才 `git push`，然後輪詢驗證上線狀態（部署到各節點會有延遲，
同一網址可能先 404 再 200，要等穩定）。

若使用者明確說「直接上」，才跳過確認步驟。

## 內部人員執行時的已知限制

這些不是缺陷，是執行前要先確認的前提。缺哪一項就先解決，不要硬跑。

**環境與權限（可事前解決）**
| 限制 | 怎麼解 |
|---|---|
| 需要網站 repo 的 git push 權限 | 請管理者把該員工的 GitHub 帳號加為 repo 協作者（Write） |
| 需要本機有 repo、git、python3 | 第一次先 clone，並確認 `python3 -c "import openpyxl"` 可執行 |
| 需要讀客戶的 Google 試算表 | (a) 客戶要把表分享給該員工 (b) 該員工的 AI 要有 Google Drive 連接器 |
| 圖片處理需要 `cwebp` | 只有要換圖時才需要，不影響純文字職缺上架 |

**必須由人判斷、AI 無法自動決定**
- **客戶自訂的標記含義**：底色、註記符號代表什麼（急件？已關閉？保留？）只有你們知道，
  每份新表都要先問過再跑
- **匿名化的descriptor**：把「某某科技」寫成「知名遊戲營運公司」還是「大型電商平台」，
  牽涉到客戶敏感度與招募吸引力的權衡
- **服務線模糊地帶**：年薪 90 萬的資深工程師算高階獵才還是一般正職？沒有硬規則
- **來源本身的錯誤**：AI 只能忠實轉寫，來源填錯薪資或條件，產出也會跟著錯——
  上架前的人工確認就是在擋這個

**流程上的注意**
- 部署後各 CDN 節點傳播不同步，同一網址可能先 404 再 200，**這是正常的**，
  要輪詢到穩定再判定成功，不要一看到 404 就以為壞了
- 客戶名稱若被畫進圖片裡（廣告圖、banner），改 HTML 無效，必須重新出圖

## 不要做的事

- 不要為了 SEO 保留客戶名稱。客戶保密優先於關鍵字。
- 不要加 `FAQPage` schema。Google 2026/5/7 起已全面移除 FAQ 豐富結果，掛了沒有效果；
  頁面上可見的 FAQ 文字照留，用一般 `<details>` 就好。
- 不要把「待確認」欄位用合理猜測填滿。寧可不寫，也不要刊錯的工作條件。
- 不要一次改動職缺頁以外的東西（首頁、文章頁）除非使用者要求。
- 不要用「A 公司／B 公司」「客戶甲／乙」或客戶代號來區隔同名職缺。那是變相洩漏客戶，
  跟直接寫客戶名一樣違規。要區隔就用班別、薪資帶、僱傭型態、外語加給、地點。
- 不要讓 `client_code` 出現在任何對外輸出（HTML／schema／網址／申請表／候選人信件）。
- 不要開一頁跟現有職缺標題與內容幾乎相同的新頁。兩頁互搶等於兩頁都排不上，
  先決定「分兩頁並做出實質差異」還是「合併／加 canonical」。
